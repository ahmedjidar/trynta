# web

The marketing site: a landing page, the documentation and a changelog. Static HTML and CSS, two
small scripts, no framework and no runtime dependency.

```
web/
  src/
    index.html          the landing page
    docs.html           the documentation — install, use, and how it works underneath
    changelog.html      the full release history
    css/site.css        HO-003's design system, as plain CSS, plus the docs layout
    js/spec.js          the landing page's disclosure rows
    js/docs.js          the docs page's contents-rail mark
    assets/
      brand/            the mark, as SVG
      fonts/            Manrope, the same two subsets the app bundles
      shots/            the app screenshots, from docs/screenshots
  dist/                 generated by `pnpm build:site`; not committed
```

Both scripts are decoration. With JavaScript off the disclosure rows are closed and the contents
rail is an unmarked list of working anchors — every word on both pages is still reachable.

## Building

```bash
pnpm build:site         # writes web/dist
npx serve web/dist      # or open web/dist/index.html directly — no server needed
```

The build does two substitutions and nothing else — no network, at build time or in the browser:

| Marker | Source |
|---|---|
| `BUILD:VERSION` | the newest release in `CHANGELOG.md` |
| `BUILD:LATEST_RELEASE`, `BUILD:RELEASES` | `CHANGELOG.md`, parsed |

A page that carries none of a marker's pairs simply gets no substitution for it — `docs.html` uses
only `BUILD:VERSION`.

**`CHANGELOG.md` is the only copy of the release notes.** This site renders it and the GitHub
release body is pasted from it (see [`docs/RELEASE-NOTES-v0.1.0-alpha.md`](../docs/RELEASE-NOTES-v0.1.0-alpha.md)).
Add a release there and rebuild; there is nothing to keep in step by hand.

## Two decisions worth knowing before you change something

**There is no star count, and adding one back is not a small change.** Three ways to produce one
were tried and all three are gone. A browser fetch hands every visitor's IP to a third party in
order to draw a number, on a page whose argument is that Trynta bundles brand icons rather than do
exactly that. A build-time fetch would have made `check:network` count three outbound call sites in
a repository whose pages claim two. A build variable leaves a slot that is empty whenever nobody
remembers to set it, which is worse than no slot. The link says Source.

**The docs page is written by hand, and it describes the shipped build.** It is not generated
from anything, which means it can go stale — so it states defaults, limits and measured numbers
rather than gesturing at them, and every one of those is checkable in the repository. When you
change a default, change it here too. The claims that are easy to get wrong are the settings
table, the two outbound requests, and the list of what is not built.

**The palette is copied from the app, and a check enforces it.** `src/theme/tokens.css` is the
source, but it cannot be imported here: it carries the whole dark theme, the row heights, the
component sizes and the z-index scale, and the site is served standalone. So `css/site.css` copies
the light palette and the scales the page draws with, and `pnpm check:site-tokens` compares 55 of
them against the app on every run. Four values deliberately differ — the WCAG corrections from
HO-003's `a11y.css` — and the check fails if one of those is reverted to its raw token too.

## Deploying

`web/dist` is a directory of static files with no server requirement. Anything that serves a
folder will do. Nothing on either page needs a build step at request time, sets a cookie, reads
storage, or makes a request to any host but the one the visitor clicks through to.
